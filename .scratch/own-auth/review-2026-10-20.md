# Build plan review, 20 October 2026

**Every finding below is now resolved in `decisions.md` (R1 to R36).**

This is a read-only review of the Implementation Guide (revision 37), checked against the design doc (6 October), the issue files under `.scratch/own-auth/issues/` and the code on `feat/own-auth`. Four reviewers each read the plan through one lens: backward dependencies, layer order, consistency with the design, and facts about the code. A separate verifier then tried to refute every finding against the guide and the code. Of the 47 findings, 42 survived and are listed below, merged where two lenses found the same thing. Line numbers point at a plain-text export of the guide, so use them as rough positions only.

**Verdict.** The order is sound top down: database, then repositories, services, guards, DTOs, use cases, controllers, then organizations, commands and tests, then web and mobile. It is not mistake-free. Five problems would break the cutover or security as written. About fifteen are places where a later layer needs something that an earlier layer does not yet contain, so you would have to go back and change it.

## 1. Would break the cutover or security (fix before starting)

1. **Maintenance mode at 0:00 has nothing behind it.** The window turns maintenance on at 0:00, but the middleware only arrives in Layer 4, and Layer 4 is deployed at 0:15. The production code running at 0:00 has no maintenance switch: `grep maintenance backend/src` finds nothing. The `onfigure` typo at `app.module.ts:67` also means that no middleware runs at all. The API therefore keeps taking writes while the snapshot is taken. The rehearsal will not catch this, because staging already runs `feat/own-auth`. *Fix:* ship the maintenance switch, with the `configure` rename, in a layer that deploys before the cutover. Alternatively, return the 503 at the load balancer.
2. **The smoke test runs while maintenance is still on.** The middleware answers 503 on every route except `/public/health`, and has no bypass. The 1:15 smoke test and the go/no-go both happen before maintenance is lifted at 2:00, and the rehearsal (step 8, then step 9) has the same order. The design doc has the same timeline. *Fix:* in Layer 4, add a bypass header or IP allow-list for the smoke-test clients, or change the order.
3. **The T-7 and T-1 announcements cannot be sent.** `announce` is a Layer 9 command, and it reaches production only at the cutover. It also emails "every non-disabled identity", but `auth_identity` stays empty until `auth:migrate` runs at 0:25 in the window. *Fix:* build the announce and reminder command before the cutover, reading recipients from the `user` table deduplicated by `lower(email)`. Keep `back` and `--release-transition` in Layer 9.
4. **Social login fails for a migrated volunteer.** Imported volunteers are `pending_password`. Social login matches them by email, links the provider and creates a session, but never sets them to `active`. The Layer 4 strategy rejects any identity that is not active, so the main social case in the design gets 401 on every request. *Fix:* in Layer 6, when a `pending_password` identity is matched, set it to active and set `emailVerifiedAt`.
5. **A null `userId` returns some other user.** TypeORM 0.3.20 (`SelectQueryBuilder.js:2468`) drops null or undefined where-keys, so `findRegularUser({ id: identity.userId })` returns the first row in the table when `userId` is null. A new volunteer with no profile would authenticate as another user, and `DELETE /mobile/user` could delete a stranger's account. *Fix:* in Layer 4, the strategies check `identity.userId` before any lookup. In Layer 7, the profile, update and delete paths reject a falsy id.

## 2. Later layers that force a change to an earlier one

**Layer 1 (database)**
- **County and city.** `RegisterOrganizationDto` and the W3 form collect `countyId` and `cityId`, but `organization` has no location column, and Layer 1 does not add one. Either add `location_id` in Layer 1 or drop both fields.
- **Event tracking.** Layer 8 records admin enable and disable through `actions_archive`. Its `event_name` column is a Postgres enum (`actions-archive.entity.ts:20`), so the new values need an `ALTER TYPE` migration, and no layer has one.
- **Unsuspend.** Unsuspending an NGO restores its admins to `active` or `pending_password`, which would also re-enable admins that were disabled individually on the Team page. This needs a `disabled_reason` column, or suspension should not touch identity status at all.
- **Deploying Layer 1 early.** The guide says Layer 1 can deploy on its own, and `migrationsRun: true` would then run the migration and its one-off "every NGO is validated" UPDATE at that deploy. NGOs created through NGO Hub between that deploy and the cutover stay unvalidated and become hidden once Layer 8 is live. The window's step "0:15 migration runs on boot" would also no longer hold. Either say that Layers 0 to 2 merge but do not deploy, or move the backfill into the cutover.

**Layer 2 (repositories)**
- **Transactions.** Set-password, register-organization and `auth:migrate` (including its `--dry-run` rollback) each run "in one transaction". Only `replaceLiveTokens` and `consume` accept a transaction manager, so identity create, update and upsert, token issue, and both revoke-all methods need an optional `manager` parameter.
- **Missing queries.** Later layers need queries that Layer 2 does not define: list super admins, find an organization's admin identities, list announce recipients, and three of the four cleanup deletes.

**Layer 3 and Layer 4 (tokens, services, guards)**
- **Mobile change-password.** It cannot tell which session is the current one. The access token has no `sid` claim, `request.user` carries no session id, and the mobile request body has no refresh token. Add `sid` in Layer 3 and expose it in Layer 4. The web version is fine, because the cookie identifies the session.
- **semver.** The version guard needs `semver` and `@types/semver` installed. `semver` is only a transitive dependency today, and `noImplicitAny` is on.
- **Redis key prefix.** Layer 10's `test:` Redis prefix needs a `REDIS_KEY_PREFIX` setting, which Layer 3 does not define.
- **Layer 3 belongs to no deploy group.** Its roughly 16 new required env vars make any image built from main unbootable until I1 is applied. Put Layer 3 in the cutover group, or make the vars optional until Layer 9.
- **Test harness.** The test database, `.env.test` and setup only exist from Layer 10, but Layer 9's `migrate-identities` spec runs "against the test database". Move the harness earlier, or rewrite that check as a unit spec. Layer 8's check also logs in as a *pending* NGO's admin, who cannot log in. It should use a confirmed but unvalidated NGO.

**Layers 5 to 7 (DTOs, use cases, controllers)**
- **Routes without use cases.** Layer 7 has routes with no Layer 6 use case behind them: `GET /auth/token/:secret`, `POST /auth/token/:secret/resend` and `POST /mobile/auth/resend-verification`. Resend also needs a Layer 3 lookup that finds a token row whatever its state, because `peekLink` returns only live rows.
- **Web resend.** On AUTH_003 the web login "offers resend", and the design promises it, but no web route resends the NGO confirmation by email. You need a DTO, a use case and `POST /auth/web/resend-…`.
- **Transition or invite.** `TokenInfoPresenter` cannot tell a transition link from a Team invite, because both are type `invite`, and W2 and W4 word them differently. Add a `purpose` field.
- **The `vic://login?email=` deep link.** It needs the plain email, but the page only receives `maskedEmail`. Return the email in the mobile-realm set-password and confirm-email answers, or drop it from the link.
- **Mobile-realm set-password.** It creates a 30-day mobile session and hands the tokens to the browser, which throws them away. Skip the session and answer the way confirm-email does.

**Layer 8 (organizations)**
- **Logos.** New uploads would store an S3 key, but about ten existing presenters pass `organization.logo` through as a full URL, which is what NGO Hub supplied. Decide in one place how a logo is served, and how old URLs and new keys live side by side.

## 3. Contradictions inside the plan

- **Disabled identity's token.** Layer 4 rejects it at once. The Layer 10 e2e test and design line 362 say it "still works for up to 15 minutes". Keep the Layer 4 behaviour and fix the other two.
- **AUTH_012 order.** Layer 6 login lists "no identity → AUTH_001" before "volunteer-only on web → AUTH_012", so AUTH_012 can never fire. State the order.
- **Re-enabling an admin.** The design's test says it sends an invite. Layer 8 sends none.
- **Link hash.** The design says the link hash is bound to `identity_id`, but the guide hashes only `type:secret`. The guide's version is the only one that works with lookup by hash, so record it as a deviation from the design.
- **AUTH_011 monitoring.** The Days 1 to 7 check watches AUTH_011 from old apps, but old builds send no `x-app-version` header and will show up as 401s instead.
- **Web 401 refresh.** W1 never refreshes on a 401 from an `/auth/` route, so `PATCH /auth/web/change-password` fails after 15 idle minutes.
- **jwks-rsa.** The design lists it under Remove. The guide rightly keeps it for the Apple verifier, so this is a correction for the design doc.
- **Contract fixed.** The guide names both Layer 5 and Layer 7 as the point where the contract is fixed.
- **Web blocking.** Web issues 13 and 14 are blocked only up to Layer 7, but W2's NGO branch and W3 use Layer 8 routes.
- **Swagger check.** Layer 5's check that "Swagger shows every DTO" cannot pass until controllers reference the DTOs in Layers 7 and 8.

## 4. Wrong facts about the existing code

- **RolesGuard.** It is global and runs *before* the controller-level JWT guards (`app.module.ts:59-63`), so `@Roles` would always return 403. The guide says it becomes usable in Layer 4.
- **Web routes.** W2 puts the Landing page at `/` under `PublicRoute`, but `/` is already the private dashboard (`Router.tsx:45-46`).
- **Mobile `AuthContext.ts`.** Its "kept" signatures import `CognitoHostedUIIdentityProvider` from Amplify, so they stop compiling once A1 removes Amplify. Add the file to A2.
- **Email templates.** The footer and `MailService` already inject `contactEmail`, `faq-tc` is never rendered, and strict mode does not need `code: null`. Layer 3's strict-render spec must supply `contactEmail` and the `asset_url` helper.
- **`IRoute`.** It lives in `common/interfaces/route.interface.ts`, not where W3 says. `FileUpload` type `doc` also accepts .doc and .docx, so the statute is not "PDF only".
- **Error codes (minor).** A Turnstile refusal and a missing statute both answer a plain 400, which W3 cannot tell apart. Duplicates can reuse the existing ORG_004.

## Refuted

The verifiers rejected five findings. The email builders do not miss `contactEmail`, because `MailService` injects it. `MAIL_CONTACT` already exists. The migration spec's duplicate email is valid, since `trim` and `lower` differ. Keeping the held emails in Redis is allowed by the guide. The guide is not inconsistent on the Send invite path or the lockout storage; the second inconsistency is in the design itself.
